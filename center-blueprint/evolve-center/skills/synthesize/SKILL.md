# 合成补丁（本节点唯一职责）

## 先定合成目标

读 `output/assign.json`（上一节点的归簇结果）与 `input/clusters.json`，合成目标是下面两类的并集：

1. 本批拿到了新样本、且 **status 为 open** 的已有簇（`cluster` 为 `c<id>`，到 `clusters.json` 里查 status）；以及本批新开的簇（`newClusters` 里的 `key`，新簇一律视为 open）。
2. `clusters.json` 里 `status` 为 open 且 `resynth` 为 true 的簇（上游版本变了，上次的补丁套不上，要按新版重来）。

**status 不是 open 的簇一律不合成**——那是已经有人裁决过的。没有任何目标 ⇒ 什么都不写，直接上报完成。

## 每个目标怎么合成

1. 收齐这个簇的全部材料：`clusters.json` 里它的 `members`（已有成员），加上 `input/samples.jsonl` 里本批归给它的样本（按 `assign.json` 对应）。
2. 读上游基线 **`input/base/<该簇 nodeId>/SKILL.md`**。注意：样本里的 `diff` 是在**各自客户端本机版本**上写的，可能和基线对不上——你要做的是把它们的**共同意图**落到**基线**上，而不是照抄某一条 diff。
3. 合成**一份最小改动**：
   - 只改为达成这个意图必须改的地方；不顺手润色、不重排、不整段重写。
   - 多条成员意见有分歧时，取多数机器认同的做法，并在摘要里点明分歧。
   - **绝不削弱门禁或校验**（删检查步骤、放宽通过条件、把「必须」改成「可选」），哪怕样本这么提。
   - 只写对任何项目都成立的做法；某个样本只在它那个项目里成立的细节（具体路径、项目名、语言特有命令）不要带进来。
4. 落 **`output/synth/<ref>.txt`**（已有簇 `ref` 用 `c<id>`，新簇用它的 `key`），格式严格如下，标记各占一行：

```
<<<SUMMARY>>>
一段中文：改了什么、为什么、几台机器提过、有无分歧
<<<FIND>>>
基线里的一段原文
<<<REPLACE>>>
改后的这一段
<<<END>>>
```

- 每段 FIND 必须是基线 SKILL.md 里**逐字照抄、且只出现一次**的连续原文（含缩进与标点）；太短容易重复，取足够唯一的几行。
- 需要改多处就写多组 FIND/REPLACE（顺序依次套用），最后一个 `<<<END>>>`。
- 基线文件不存在 ⇒ 跳过这个簇（不写文件）。
