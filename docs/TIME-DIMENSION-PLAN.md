# 看板时间维度 · 三期设计

> **背景**：工作流页与用户页原本只有「区间累计总量」——每个实体一行数字、一张排名图，**没有任何"何时"的信息**。于是看不出谁在涨谁在跌、谁已经不用了、大家什么时候在用。趋势页虽有逐日曲线，但只有全局口径，无法下钻到单个工作流/用户。
>
> 本文是这套补齐方案的**决策留档**：写清每个分叉选了什么、为什么、以及放弃了什么。P1 已落地；P2/P3 照此执行，不必重新推导。

## 交付切分（按 schema 风险递增）

| 期 | 内容 | schema 改动 | 回填 | 状态 |
|---|---|---|---|---|
| **P1** | 逐日时序下钻 + 环比 | **无** | 无 | ✅ 已落地 |
| **P2** | 最近活跃 / 沉默天数 | `ALTER ADD COLUMN` ×2 | 需要 | 待做 |
| **P3** | 使用时段分布（作息） | 新表 `daily_hour` | 需要 | 待做 |

这样切是刻意的：P1 零 schema 零回填、当天可上线可回滚；风险最高的 P3（引入第二套时间口径）放最后，前两期的价值不被它拖住。**任何一期出问题，`git revert` 服务端代码即可——增量 DDL 留在库里无害，不需要反向迁移脚本。**

## P1 · 逐日时序 + 环比（已落地）

### 落点
- **主表**新增一列环比，**跟随当前排序列**：按 `runs` 排就显 `runs` 的环比，改排 `Token` 就变 `Token` 的环比。表永远只多一列、只有一个箭头，且总与当下关注的指标对齐。
- **点行展开**详情面板：该实体自己的日曲线 + 「本期 vs 上期」对比条。一次只开一行。

### 关键决策

**环比对比窗两端都截至昨日**（`lib/stats.js::compareWindows`）。
主表总量与日曲线**仍含今日**（那是实时感），但环比另起两个等长的完整自然日窗口。理由：range 末尾的「今天」只过了一半，直接拿它当分子会让每天上午一片飘红、下午转绿——那是钟点噪声不是趋势信号。曲线末点压暗 40% 并在标题标「末柱为当日，数据不完整」。

> 提示文字刻意放在**图外**：一格类目只有 30~40px 宽，ECharts `markArea` 的图内标签在窄图/长区间下必被 grid 裁掉（实测已验证）。

**小基数改显绝对差**（`core/fmt.js::fmtDelta`）。两期任一 < 10 时不显百分比。长尾工作流从 1 涨到 3 就是 `+200%`，在表里比真正重要的 `+18%`（312→368）还刺眼——那是噪声不是信号。上期为 0 也走这一支，顺带避开除零。

**契约纯增量**：`/stats/blueprints` 与 `/stats/users/top` 新增 `compare` 与每行 `cur`/`prev`，旧字段一个不动；下钻另开两个端点。`compare` 为 `null`（各行不带 `cur`/`prev`）当且仅当 range 内没有一整个完整自然日。

**不为下钻加索引**：`daily_user` 按 `user/host` 过滤要扫范围内全部行（90 天千人 ≈ 9 万行、十毫秒级），但这是按需下钻而非首屏，不值得为它动 schema 破坏 P1 的「零 DDL」承诺。

## P2 · 最近活跃 / 沉默天数（待做）

### 要回答的问题
「现在到底还有谁在用、哪些工作流已经没人跑了。」

### 核心矛盾（必须先理解，否则做出来是废的）
区间聚合**天然回答不了这个问题**：一个 30 天没人跑的工作流，在「近 30 天」视图下压根不在结果集里——给主表加「沉默天数」列也没用，那一行根本渲染不出来。所以必须显式把沉默实体捞回结果集。

### 决策

**recency 口径 = 只算实质使用**。只认 `session_start`/`session_end`/`bp_run_end`/`failure_event`，**心跳与 `instance_online` 一律不算**。
> 陷阱：`installs.last_seen` 看起来白送（秒级精度），但它含心跳——客户端每 5 分钟跳一次，装了挂着从不用的人 `last_seen` 永远是「5 分钟前」。照那个口径看板会显示**全员活跃**，恰好把要看的东西盖住。

**`last_at` 取 `client_ts`**（事件真实发生时刻），异常/缺失时回落 `server_ts`。
> 用 `server_ts` 的失效方向是**过报新鲜度**：断网 3 天后重连补发，实际已沉默 3 天的实体会显示「今天活跃」。异常判据只有单向的「`client_ts` > `server_ts` + 5min」（时钟走快，物理不可能）——`client_ts` 比 `server_ts` 早很多是**正常**的，那就是补发，拿"差值大"当异常判据会把所有断网用户的真实活跃时刻全删掉。

**实现 = 加列不加表**：`daily_user.last_at` + `daily_blueprint.last_at`，ingest 顺手 `MAX` 更新。
recency 查询**不带 range 全表取 `MAX(last_at)`**（`daily_blueprint` 一年约 1 万行、`daily_user` 约 36 万行）——只有不受 range 约束才能看见沉默实体。

**结果集两页分治**：
- 工作流页：**返回全量**（含沉默，指标补 0）。反正就几十个，默认按 `runs` 降序沉默的自然沉底，点「沉默」列排序就捞上来。
- 用户页：保持 Top N，给现有 metric 分段控件**加一个「沉默天数」选项**——切过去就是流失排行榜。零新交互概念。

**沉默工作流的准入线：历史累计 `runs ≥ 3`**。
> `blueprintId` 是**用户可控且只增不减**的（蚕丛支持自建/复制蓝图，`bp-` 是保留前缀，用户 id 走 `USER_ID_RE`）。千人跑一两年，历史累计几百上千个 id 完全可能，绝大多数是「建了跑一次就废」的实验品。不设准入线，沉默名单会被它们淹没，恰好埋掉真正想找的「曾经在用、现在不用了」。表底标「已隐藏 N 个累计运行 <3 次的工作流」保留可见性。用户页**不设**准入线——`user@host` 来自真实机器，基数受人数约束，这是有意的不对称。

**沉默阈值相对当前 range**：range 内零活动即沉默，超 **2×range** 才给 ⚠。不写死常量——切 7 天看短期异常、切 90 天看长期流失，阈值随关注窗口自适应。

**CSV 跟进**：`blueprints`/`users` 两个导出各加「上次活跃」「沉默天数」两列，`users` 同步纳入沉默用户。环比不进（派生比较值，接收方拿原始数自己能算）。
> 这条是纪律不是可选项——`/v1/export/*` 一直与看板严格同口径，不跟进下次就是对账事故。

### 迁移
1. `DDL_V4` 只有两条 `ALTER TABLE ... ADD COLUMN last_at TEXT`。SQLite 的 `ADD COLUMN`（可空、无 DEFAULT、无约束）是**纯元数据操作**，不重写表、O(1)，几百万行也是毫秒级 —— 故随启动自动迁移不会碰 systemd 的 `TimeoutStartSec`。
2. 回填走**独立 `npm run backfill`**（与现有 `npm run migrate` 同模式），**不塞进迁移事务**。近 90 天从 `events` 精确回填；更早的用 `daily_*` 的 `MAX(day)` 兜底成日精度。
3. **逐日一个事务**，不是一个大事务。WAL 下单写者+多读者，每个事务只处理一天，锁持有时间在百毫秒级，`busy_timeout=5000` 兜底争锁。就算真把 ingest 卡住也不丢数据——客户端 fail-open + spool 补发是设计内的背压。
4. **幂等**：每天先 `DELETE` 该日区间再 `INSERT`，复用现有 `recomputeDaily*` 的写法，中断了直接重跑。
5. `last_at` 必须进 `aggregate.js` 的 `recompute*` 家族，否则它是库里唯一不会自愈的字段。
6. 前端要先把 `last_at == null` 的渲染路径写好（显示 `—`），否则迁移后、回填前的窗口期页面会花。
7. `scripts/seed-demo.js` 同步补新字段。

## P3 · 使用时段分布 / 作息（待做）

### 落点
- 趋势页加**第三个模式「作息」**（现有 `[按日期][实时]` 分段控件加一项）——三个模式恰好是三个时间尺度：日（趋势）/ 分钟（实时）/ 周×时（结构）。
- 工作流详情面板加 24×7 热力图。**用户页不做**——「某个人几点上班」决策价值最低、行数代价最高，且容易滑向监工。

### 决策

**粒度 = 全局 + 工作流两层**，新表 `daily_hour(day, hour, blueprint_id)`，`blueprint_id = ''` 存全局行。

| 粒度 | 行数/天 | 一年累计（永久保留） |
|---|---|---|
| 全局 | 24 | 8,760 |
| + `blueprint_id`（设 30 个工作流） | ~720 | **26 万**（可接受） |
| + `user`（千人） | ~24,000 | 876 万 —— 会成为库里最大的表，**否决** |

> ⚠️ **全局行 ≠ 各工作流行之和**：会话类事件没有 `blueprintId`，只进全局行。以后一定有人拿这两个对账然后报 bug，文档和 UI 都要写明。

**必须预聚合，不能扫 events 现算**。时段分布要扫全类型，30 天约 240 万行。参照已有教训：30 天 11.7 万条 `failure_event` 做 `json_extract + GROUP BY` 就要 ~1 秒（那正是当初新建 `daily_fail` 的原因），这里大 20 倍，必是秒级，memo 也只能摊薄、首次仍卡。

**小时基准取 `client_ts` 而非 `server_ts`**，`day` 也取 `client_ts`，**表内自洽**。
> 用 `server_ts` 的话，断网补发会把尖峰全堆到重连时刻——一个凌晨 3 点重连补发的批会凭空长出一根凌晨高峰柱，图直接是假的。
> `day` 也必须同源：若 `day` 用 server 而 `hour` 用 client，一个「昨天 23:00 发生、今早 09:00 补发」的事件会记成 `day=今天, hour=23`——今天这一行冒出一根 23 点的柱子，而今天 23 点还没到；24×7 热力图里跨午夜的事件还会落进错的格子。
> **代价（必须写进设计文档）**：`daily_hour.day` 与 `daily_*.day` 是两套口径，**两表永不可 join / 对账**。

**⚠️ 实现要点：`client_ts` 是 UTC，不能字符串切片。**
`TechDemos/server-telemetry/index.js` 发的是 `new Date(now()).toISOString()`，`toISOString()` **恒返回 UTC**（`...Z`）。设计文档与 `CLIENT-HANDOFF.md` 里 `"2026-07-04T09:30:00+08:00"` 那个示例**从来没对过**——`ts` 被标为「选填、仅留档」，没人有义务守它，也没有 parity 用例守它。
- 因此必须 `new Date(client_ts)` 解析后取**服务器本地**日/时，而不是 `ts.slice(0,10)` / `ts.slice(11,13)`（那样对 Asia/Shanghai 会整整差 8 小时，图上全员凌晨 1 点上班）。
- **不要改客户端**：改了要发版、等全量铺开，铺开期内 `client_ts` 混着 `Z` 和 `+08:00` 两种格式，服务端还得写格式嗅探——比服务端统一转换糟糕得多。
- 顺带把 `ts` 在 `CLIENT-HANDOFF.md` 里**从「仅留档」升格为「作息维度的权威源，建议必填」**，并在 `event-registry` parity 用例加一条守卫，防止哪天有人改成本地格式静默毁掉热力图。

**时钟异常单向阀**：仅当 `client_ts > server_ts + 5min`（时钟走快，物理不可能）或不可解析时，把该事件剔出时段统计并**计数**。丢弃数记进 `meta` 表，由 `/v1/stats/hours` 带出、在热力图面板脚注显示——否则这个丢弃是静默的，没人会发现口径在漏数据。

**热力图窗口固定近 30 天，不跟随顶栏 range**。面板标题直写「作息分布 · 近 30 天」。
> 7 天档下每个「周几×小时」格子只有 1 个样本——那不是作息规律是随机噪声，而图看起来很有信息量，比没有图更糟。全局 range 的语义是「统计区间」，作息规律是个相对稳定的结构量，两者本就不该同步。

### 迁移
同 P2 的四步（建表毫秒级 → 独立回填脚本 → 逐日事务 → 进 `recompute*` 家族），外加：
- `daily_hour` **永久保留、不进 90 天清理**（它不是 events）。
- 回填**只能覆盖近 90 天**，更早的 `events` 已被夜间 job 清掉，物理上无法重建——那段永远空白，UI 要标注数据起始日。
- TZ 约束升级，见 [DEPLOYMENT.md §4.1](./DEPLOYMENT.md#41-改-tz-对作息维度的额外破坏规划中见-time-dimension-planmd-p3)。

## 明确放弃的东西

| 想过但没做 | 原因 |
|---|---|
| 详情面板里放交叉维度（该工作流的 Top 用户 / 该用户的 Top 工作流） | 需新建 `daily_user_blueprint` 交叉聚合表，已超出「补时间维度」的范围 |
| 详情面板里放「最近 N 次运行明细」 | `events` 上无 `blueprint`/`user` 索引，要么扫全表 + `json_extract`（秒级）要么新增索引加重写路径；且只能看 90 天 |
| 用户级时段分布 | 行数爆炸（一年 876 万行永久表）+ 决策价值最低 + 容易被当监工工具 |
| 自定义日期区间选择器 | 顶栏 7/30/90 三档够用；`parseRange` 本就支持任意 `from`/`to`，真需要时前端加控件即可 |
| 按实体自身节奏判定沉默（对比历史间隔中位数） | 最"智能"但「为什么这个标黄了」无法解释；相对 range 的规则一句话说得清 |
